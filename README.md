# Doc Checker

Сервер на Java (Spring Boot) с локальной LLM через Ollama. В нём два модуля:

1. **Поиск персональных данных (152-ФЗ)** — основной. Принимает файл или zip-архив, определяет по каждому файлу, есть ли персональные данные, и показывает **найденные признаки, место обнаружения (путь к файлу с названием и позиция внутри файла) и объяснение со ссылкой на норму закона**.
2. **Проверка по требованиям** — проверяет JPEG/PNG/PDF/DOCX на соблюдение заданных требований (см. раздел в конце).

Правовая рамка: система **только выявляет наличие признаков персональных данных**. Она не оценивает законность обработки, наличие согласия или возможность публикации; согласие и открытый доступ не отменяют факт наличия данных. Эта оговорка выводится в интерфейсе и в выгрузках.

## Запуск

```bash
docker compose up --build        # Redis + Ollama + приложение, модель gemma3:4b скачивается автоматически
```

Или локально (нужны Java 21, Maven, Ollama, Redis):

```bash
ollama pull gemma3:4b
docker run -d -p 6379:6379 redis:7-alpine          # либо --app.storage.type=memory
mvn spring-boot:run
```

- Веб-интерфейс: http://localhost:8080/
- Swagger: http://localhost:8080/swagger-ui.html
- Состояние Ollama, моделей и Redis: `GET /api/health`

Модели и лимиты настраиваются в `application.yml` (раздел `app.pd` и `app.ollama`).

## Веб-интерфейс

Загрузите файл или zip-архив (можно перетащить). Во время проверки видны прогресс и текущий файл, результаты появляются по мере готовности. Для каждого файла показаны вердикт, путь (включая путь внутри архива), таблица находок (тип, значение, место, уверенность, метод, норма и объяснение), заметки и журнал шагов агента. Найденные значения отображаются в виде чёрных полос вымарывания. Есть фильтр по вердикту, поиск по пути и выгрузка в CSV и JSON.

## Что умеет

**Форматы:** docx, doc, rtf, pdf, html, md, txt, csv, json (и JSON Lines), parquet, xlsx, png, jpg, gif, tif, bmp, а также zip-архивы (рекурсивно, до 3 уровней вложенности). Тип определяется по содержимому, а не по расширению. Остальные форматы получают статус `UNSUPPORTED` и вердикт `UNDETERMINED`, а не «данных нет».

| Формат | Что извлекается | Как указывается место |
|---|---|---|
| docx | абзацы, таблицы (подписи полей), колонтитулы, сноски, примечания и их авторы, текстовые поля, автор документа, встроенные изображения | `абзац 12`, `таблица 1, строка 2, ячейка 2` |
| doc, rtf | текст, колонтитулы, автор, встроенные изображения (doc); кодовая страница 1251 (rtf) | `абзац N` |
| pdf | текст по страницам, поля форм, автор; страницы без текста и крупные встроенные картинки отправляются в vision-модель | `стр. 3`, `стр. 3 (скан)` |
| html | видимый текст по блокам, mailto/tel-ссылки, значения полей форм, атрибуты alt и title, мета-автор | CSS-селектор элемента |
| csv, xlsx, parquet | заголовки и значения всех ячеек (xlsx — все листы, включая скрытые) | `строка 14, столбец «снилс»`, `лист «Кадры», C14` |
| json | ключи и значения | `$.users[3].phone` |
| txt, md | строки; кодировка определяется автоматически (UTF-8, cp1251, KOI8-R, cp866) | `строка N` |
| png, jpg, gif, tif, bmp | кадры и страницы в vision-модель, EXIF (автор, GPS) | `изображение`, `кадр 2`, `страница 3` |

Имена файлов в zip с кириллицей (cp866, cp1251 или UTF-8) восстанавливаются автоматически. Архив защищён лимитами на число файлов, размер, вложенность и степень сжатия, файлы на диск не распаковываются.

**Поиск признаков** (агент выбирает шаги по формату и результатам, каждый шаг записывается в журнал):

1. **Правила и контрольные суммы** (без LLM, быстро): СНИЛС (контрольное число), ИНН физлица из 12 цифр (две контрольные суммы; десятизначный ИНН организации не считается), банковская карта (алгоритм Луна), паспорт и водительское удостоверение (по контексту), телефон, email (ролевые ящики вроде `info@` — слабый признак), дата рождения (только рядом со словом о рождении), ФИО по шаблонам (включая падежи и инициалы), адрес (улица + дом + квартира; фразы «зарегистрирован по адресу»), явные подписи «Диагноз:», «Национальность:» и т. п., значения в столбцах и полях с названиями вроде «ФИО», «Телефон», «СНИЛС».
2. **LLM по тексту:** ФИО без шаблона, адреса, здоровье, национальность, убеждения, судимость. Цитата модели принимается, только если дословно найдена в исходном тексте (защита от выдумок).
3. **Vision-модель по изображениям:** переписывает читаемый текст (он затем проходит те же правила) и отмечает лица. Уверенность по найденному на изображениях ограничена 0,85.
4. **Объединение:** совпадение двух методов повышает уверенность. Значения маскируются (`***-***-*** 95`).
5. **Структура данных:** название поля, предназначенного для персональных данных, — слабый признак.

**Вердикты по файлу:** `YES` — есть признак с уверенностью ≥ 0,6; `NO` — ничего не найдено и файл разобран полностью; `UNDETERMINED` — есть только слабые признаки, либо файл не разобран или разобран частично (например, изображение при недоступной модели). Статусы разбора: `OK`, `PARTIAL`, `UNSUPPORTED`, `ERROR`.

## Правовая привязка

Справочник «тип признака → норма и объяснение» лежит в `src/main/resources/pd/legal-basis.json`. Его можно заменить без пересборки: `app.pd.legal-basis-file=/path/to/legal-basis.json`. Текущее содержимое:

| Признаки | Норма |
|---|---|
| ФИО, СНИЛС, ИНН, паспорт, водительское удостоверение, карта, телефон, email, дата рождения, адрес и место рождения, автор в метаданных, геопозиция | ст. 3 п. 1 (определение персональных данных) |
| Изображение лица | ст. 3 п. 1; ст. 11 (биометрические данные, если используются для установления личности) |
| Здоровье, расовая и национальная принадлежность, религиозные и философские убеждения, политические взгляды, интимная жизнь | ст. 10 ч. 1 (специальные категории) |
| Сведения о судимости | ст. 10 ч. 3 |

Соответствие нужно **проверить юристу по актуальной редакции закона**: закон менялся неоднократно, а разделение «иные / специальные / биометрические» зависит от контекста обработки, который система не оценивает.

## API

| Метод | Назначение |
|---|---|
| `POST /api/scans` | multipart: `file` (файл или zip), `useLlm` (по умолчанию `true`). Ответ 202 с `id` |
| `GET /api/scans/{id}` | статус, прогресс, счётчики, сводка по типам и нормам |
| `GET /api/scans/{id}/files?verdict=&q=&page=&size=` | отчёты по файлам: вердикт, находки, заметки, журнал шагов |
| `GET /api/scans/{id}/export?format=csv\|json` | выгрузка отчёта |
| `GET /api/pd/legal-basis` | справочник норм |
| `DELETE /api/scans/{id}` | удалить результаты |

Постман-коллекция: `postman/doc-checker.postman_collection.json`.

## Конфигурация (раздел `app.pd`)

| Параметр | По умолчанию | Описание |
|---|---|---|
| `mask-values` | `true` | маскировать значения в отчёте и хранилище |
| `yes-threshold` / `min-confidence` | `0.6` / `0.4` | порог подтверждения и порог отбрасывания |
| `llm-enabled`, `vision-enabled` | `true` | LLM по тексту и vision по изображениям |
| `llm-max-chars-per-file` | `30000` | сколько текста файла отдавать LLM (остальное проверяется правилами) |
| `max-images-per-file`, `max-frames` | `10`, `5` | лимиты изображений и кадров на файл |
| `max-archive-entries`, `max-entry-bytes`, `max-archive-total-bytes`, `max-archive-depth` | `5000`, `100 МБ`, `1 ГБ`, `3` | лимиты архива |
| `workers`, `queue-capacity` | `1`, `5` | очередь сканирований (Ollama плохо параллелит запросы) |
| `result-ttl` | `24h` | срок хранения результатов |

Размер загружаемого файла ограничен `spring.servlet.multipart.max-file-size` (по умолчанию 500 МБ). Файл сначала сохраняется во временный каталог и удаляется после обработки.

## Модели

По умолчанию используется одна мультимодальная модель `gemma3:4b`. Можно разделить: `OLLAMA_TEXT_MODEL=qwen3:4b OLLAMA_VISION_MODEL=qwen3-vl:4b`. Актуальные теги проверяйте на https://ollama.com/library. На процессоре проверка изображений и LLM-поиск заметно медленнее, чем правила: для больших архивов можно отключить `useLlm` в интерфейсе или в запросе.

## Тесты

```bash
mvn test
```

Тесты не требуют Redis и Ollama (in-memory хранилище, подставная LLM). Сквозной тест `PdScanFlowTest` собирает zip с docx, pdf, csv, json, html, parquet, png и txt (имена в cp866) и проверяет пути, находки, маскирование и нормы.

## Ограничения

- **Качество vision-модели.** Малые модели (3–4 млрд параметров) ошибаются в чтении мелкого текста и рукописи, а распознавание лиц они делают приблизительно. Отдельного OCR (Tesseract) и детектора лиц (OpenCV) пока нет.
- **Агент.** Шаги выбираются кодом по формату и результатам (оркестратор с журналом шагов), а не свободным выбором инструментов самой моделью.
- **Не поддерживаются:** pptx, odt, xls, rar, 7z, tar, webp и др. Они получают статус `UNSUPPORTED`.
- **Оформление и скрытое содержимое** документов анализируется не полностью (например, текст внутри векторных объектов PDF, изменения и скрытый текст DOCX).
- **Вердикт `NO` означает «не найдено доступными методами»**, а не гарантию отсутствия данных, особенно в изображениях.
- Проверки в статусе `RUNNING` не возобновляются после перезапуска.
- Аутентификации нет; сервис рассчитан на внутреннюю сеть.

## Модуль 2: проверка по требованиям

`POST /api/requirement-sets` — загрузить требования (текст или txt, md, docx, pdf), `POST /api/checks` — отправить файл (JPEG/PNG/PDF/DOCX), `GET /api/checks/{id}` — результат по каждому требованию (`PASS`, `FAIL`, `UNKNOWN`) и краткая сводка. Подробности — в Swagger (раздел «Требования» и «Проверки»).
