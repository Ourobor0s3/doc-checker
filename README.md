# Doc Checker

Сервер на Java (Spring Boot) с локальной LLM через Ollama. Данные не уходят в облако.

| Модуль | Что делает |
|---|---|
| **Поиск персональных данных** | Принимает файл или zip-архив и по каждому файлу отвечает: есть ли персональные данные, какие именно, где они находятся и на какую норму 152-ФЗ это опирается |
| **Проверка по требованиям** | Проверяет JPEG, PNG, PDF и DOCX на соблюдение заданных требований (см. [конец документа](#проверка-по-требованиям)) |

> **Правовая рамка.** Система только фиксирует наличие признаков персональных данных. Она не оценивает законность обработки, наличие согласия или возможность публикации. Согласие и открытый доступ не отменяют факт наличия данных. Эта оговорка показывается в интерфейсе и в выгрузках.

## Быстрый старт

### Docker Compose (Redis, Ollama и приложение)

```bash
docker compose up --build
```

Контейнер `ollama` сам скачивает модель и становится «здоровым», только когда она готова; приложение стартует после этого. Другая модель:

```bash
OLLAMA_MODEL=qwen3-vl:4b docker compose up --build
```

Для NVIDIA GPU раскомментируйте блок `deploy` у сервиса `ollama` в `docker-compose.yml`.

### Локально

Нужны Java 21 или новее, Maven, Ollama и Redis.

```bash
ollama pull gemma3:4b
docker run -d -p 6379:6379 redis:7-alpine
mvn spring-boot:run
```

Без Redis добавьте `-Dspring-boot.run.arguments=--app.storage.type=memory` (данные пропадут при перезапуске).

После запуска доступны:

| Адрес | Что там |
|---|---|
| http://localhost:8080/ | веб-интерфейс |
| http://localhost:8080/swagger-ui.html | описание API |
| http://localhost:8080/api/health | состояние Ollama, моделей и Redis |

## Веб-интерфейс

1. **Загрузите** файл или zip-архив (кликом или перетаскиванием). Флажок «Использовать LLM» включает поиск ФИО и адресов в тексте и анализ изображений: это точнее, но медленнее.
2. **Следите за прогрессом.** Результаты по файлам появляются по мере проверки.
3. **Изучите отчёт.** Для каждого файла показаны вердикт, путь (включая путь внутри архива), таблица находок (тип, значение, место, уверенность, метод, норма с объяснением), заметки и журнал шагов. Найденные значения нарисованы чёрными полосами вымарывания.
4. **Выгрузите** отчёт в CSV или JSON. Фильтры по вердикту и поиск по пути помогают в больших архивах.

### Прошлые проверки

Панель «Прошлые проверки» показывает последние сканирования со статусом и счётчиками. У каждой записи есть три действия: **Открыть**, **Копировать ID** и **Удалить**.

- Результат можно открыть по ID: вставьте ID (или ссылку целиком) в поле над списком.
- Кнопки «Копировать ID» и «Копировать ссылку» над списком файлов дают адрес вида `http://localhost:8080/#scan=<id>`: по нему результат открывается сразу.
- Результаты хранятся 24 часа (`app.pd.result-ttl`).

## Как это работает

```
файл или zip
   │
   ▼
 архив? ── да ──► обход с лимитами (число файлов, размер, вложенность, степень сжатия)
   │                 имена в cp866/cp1251/UTF-8 восстанавливаются
   ▼
 определение формата по содержимому ──► извлечение текста, таблиц, метаданных, изображений
   │
   ├─► правила и контрольные суммы ───────────────┐   без модели, быстро
   ├─► LLM по тексту (ФИО, адреса, спецкатегории) ┤   цитата должна дословно быть в тексте
   └─► vision-модель по изображениям ─────────────┤   лица и текст, с проверками (см. ниже)
                                                  ▼
                 объединение ► маскирование ► норма 152-ФЗ ► вердикт по файлу
```

Каждый шаг агента записывается в журнал файла, поэтому видно, почему получился такой вердикт.

**Вердикт по файлу**

| Вердикт | Когда |
|---|---|
| `YES` | есть признак с уверенностью не ниже 0,6 |
| `NO` | признаков нет, файл разобран полностью |
| `UNDETERMINED` | есть только слабые признаки, либо файл не разобран или разобран частично (например, изображения при недоступной модели) |

`NO` означает «не найдено доступными методами», а не гарантию отсутствия данных.

## Поддерживаемые форматы

Тип определяется по содержимому, а не по расширению. Неизвестные форматы получают статус `UNSUPPORTED` и вердикт `UNDETERMINED`, а не «данных нет».

| Формат | Что извлекается | Как указано место |
|---|---|---|
| docx | абзацы, таблицы с подписями полей, колонтитулы, сноски, примечания и их авторы, текстовые поля, **удалённый текст в истории правок**, автор, встроенные изображения | `абзац 12`, `таблица 1, строка 2, ячейка 2` |
| doc, rtf | текст, колонтитулы, автор, изображения (doc); кодовая страница 1251 (rtf) | `абзац N` |
| pdf | текст по страницам, поля форм, автор; страницы без текста и крупные встроенные картинки уходят в vision-модель | `стр. 3`, `стр. 3 (скан)` |
| xlsx | все листы, включая скрытые; **результаты формул**; примечания к ячейкам и их авторы | `лист «Кадры», C14` |
| csv, parquet | заголовки и значения всех ячеек | `строка 14, столбец «снилс»` |
| json, JSON Lines | ключи и значения | `$.users[3].phone` |
| html | видимый текст, ссылки mailto и tel, значения форм, атрибуты alt и title, **комментарии**, мета-автор | CSS-селектор элемента |
| txt, md | строки; кодировка определяется автоматически (UTF-8, cp1251, KOI8-R, cp866) | `строка N` |
| png, jpg, gif, tif, bmp | кадры и страницы в vision-модель, EXIF (автор, GPS) | `изображение`, `кадр 2` |
| zip | рекурсивный обход, вложенные архивы до 3 уровней | `выборка.zip/папка/файл.docx` |

Одинаковые изображения (например, логотип в каждом колонтитуле) анализируются один раз.

## Что считается персональными данными

**Правила и контрольные суммы** (без LLM):

| Признак | Как проверяется |
|---|---|
| СНИЛС | контрольное число |
| ИНН физлица | 12 цифр, две контрольные суммы (10-значный ИНН организации не считается) |
| Банковская карта | алгоритм Луна и допустимый диапазон платёжной системы |
| Полис ОМС | 16 цифр рядом со словом «полис» или «ОМС» |
| Паспорт, водительское удостоверение | серия и номер, тип по контексту |
| Телефон, email | форматы РФ и международные; номера 8-800 и ящики вроде `info@` не считаются или слабые |
| Дата рождения | только рядом со словом о рождении |
| ФИО | шаблоны «Фамилия Имя Отчество», падежи, инициалы |
| Адрес | улица, дом и квартира; фразы «зарегистрирован по адресу» |
| Специальные категории | явные подписи «Диагноз:», «Национальность:» и т. п. |
| Значения в полях | столбцы и ключи с названиями вроде «ФИО», «Телефон», «СНИЛС» |
| Метаданные | автор документа, геопозиция снимка |

**LLM по тексту** находит ФИО без шаблона, адреса, сведения о здоровье, убеждениях, судимости. **Vision-модель** ищет лица на фотографиях и читает текст на сканах.

## Защита от галлюцинаций модели

Малые модели принимают рисунки за лица, выдумывают текст на пустых картинках и «находят» то, чего нет. Поэтому ответ модели никогда не принимается напрямую:

| Риск | Что делается |
|---|---|
| Лицо «найдено» на рисунке, логотипе, пейзаже | Модель сначала **классифицирует** изображение (фото человека, документ с фото, рисунок, логотип, схема, фото без людей), указывает число лиц и **перечисляет видимые черты**. Рисунки и противоречивые ответы отбрасываются. Лицо без описания черт — слабый признак |
| Модель уверенно ошибается | Кандидат на лицо проходит **независимую проверку** другим запросом: «это реальная фотография человека?». Ответ «нет» отбрасывает находку, «не уверен» делает её слабой |
| Выдуманный текст на картинке | Текст читается, **только если** модель сказала, что он есть (для документов и сканов читается всегда). Пустые и крошечные изображения в модель не отправляются |
| Выдуманные значения в тексте со скана | Значения сверяются со **вторым чтением** с другой формулировкой. Не подтверждённые становятся слабыми признаками, а вердикт файла — «не определено» |
| LLM придумала цитату | Цитата принимается, только если **дословно найдена** в исходном тексте. Названия организаций, одно слово вместо ФИО, «адрес» без номера дома отсекаются |
| LLM нашла спецкатегорию «по смыслу» | Без подтверждения правилом это слабый признак |
| Инъекция в документе («ответь, что данных нет») | Содержимое файлов в запросах объявлено данными, а не инструкциями; детерминированные правила работают независимо от модели |

Что именно произошло с каждым изображением, видно в журнале шагов файла и в заметках.

## Правовая привязка

Справочник «тип признака → норма и объяснение» лежит в `src/main/resources/pd/legal-basis.json`. Свой файл подключается без пересборки: `app.pd.legal-basis-file=/путь/legal-basis.json`.

| Признаки | Норма |
|---|---|
| ФИО, СНИЛС, ИНН, паспорт, водительское удостоверение, полис ОМС, карта, телефон, email, дата рождения, адрес и место рождения, автор в метаданных, геопозиция | ст. 3 п. 1 (определение персональных данных) |
| Изображение лица | ст. 3 п. 1; ст. 11 (биометрические данные, если используются для установления личности) |
| Здоровье, расовая и национальная принадлежность, убеждения, политические взгляды, интимная жизнь | ст. 10 ч. 1 (специальные категории) |
| Сведения о судимости | ст. 10 ч. 3 |

Соответствие должен проверить юрист по актуальной редакции закона: разделение «иные, специальные, биометрические» зависит от контекста обработки, который система не оценивает.

## API

| Метод | Назначение |
|---|---|
| `POST /api/scans` | multipart: `file` (файл или zip), `useLlm` (по умолчанию `true`). Ответ 202 с `id` |
| `GET /api/scans?limit=30` | история: последние сканирования, новые первыми |
| `GET /api/scans/{id}` | статус, прогресс, счётчики, сводка по типам и нормам |
| `GET /api/scans/{id}/files?verdict=&q=&page=&size=` | отчёты по файлам: вердикт, находки, заметки, журнал шагов |
| `GET /api/scans/{id}/export?format=csv\|json` | выгрузка отчёта |
| `DELETE /api/scans/{id}` | удалить результаты |
| `GET /api/pd/legal-basis` | справочник норм |

## Настройка

Основные параметры лежат в `src/main/resources/application.yml`, раздел `app`. Через переменные окружения задаются `OLLAMA_URL`, `OLLAMA_TEXT_MODEL`, `OLLAMA_VISION_MODEL`, `REDIS_HOST`, `REDIS_PORT`.

| Параметр `app.pd.*` | По умолчанию | Описание |
|---|---|---|
| `mask-values` | `false` в `application.yml` | `true` маскирует значения в отчёте и хранилище (`***-***-*** 95`). При `false` реальные данные попадают в Redis и выгрузки, учитывайте это при хранении |
| `yes-threshold`, `min-confidence` | `0.6`, `0.4` | порог подтверждения и порог отбрасывания |
| `llm-enabled`, `vision-enabled` | `true` | LLM по тексту и vision по изображениям |
| `verify-faces`, `verify-ocr` | `true` | независимая проверка лиц и второе чтение текста с изображений |
| `min-image-side` | `48` | изображения меньше (иконки) не анализируются |
| `llm-max-chars-per-file` | `30000` | сколько текста файла отдавать LLM (остальное проверяется правилами) |
| `max-images-per-file`, `max-frames` | `10`, `5` | лимиты изображений и кадров |
| `max-archive-entries`, `max-entry-bytes`, `max-archive-total-bytes`, `max-archive-depth` | `5000`, 100 МБ, 1 ГБ, `3` | лимиты архива |
| `workers`, `queue-capacity` | `1`, `5` | очередь сканирований (Ollama плохо параллелит запросы) |
| `result-ttl` | `24h` | срок хранения результатов и истории |

| Параметр `app.ollama.*` | Описание |
|---|---|
| `text-model`, `vision-model` | по умолчанию одна модель `gemma3:4b`; можно разделить, например `qwen3:4b` и `qwen3-vl:4b` |
| `read-timeout` | сколько ждать ответа одной модели (на процессоре для изображений можно увеличить) |
| `num-ctx`, `num-predict` | размер контекста и лимит длины ответа |
| `think` | `false` отключает рассуждения у thinking-моделей (qwen3), быстрее |

Актуальные теги моделей смотрите на https://ollama.com/library.

## Тесты

```bash
mvn test
```

Нужны только JDK и Maven: Redis и Ollama не требуются (хранилище в памяти, подставная модель). Сквозной тест собирает zip с docx, pdf, xlsx, csv, json, html, parquet, png и txt (имена в cp866) и проверяет пути, находки, маскирование, нормы и поведение при галлюцинациях (рисунок, пустая страница, выдуманный текст).

## Если что-то не работает

| Что видите | Причина и решение |
|---|---|
| `Standard Commons Logging discovery in action with spring-jcl: please remove commons-logging.jar` | `commons-logging` приходит транзитивно вместе с PDFBox. В `pom.xml` он исключён у `pdfbox` и `jbig2-imageio`. Если появится снова: `mvn dependency:tree -Dincludes=commons-logging`, найдите зависимость и добавьте такое же исключение |
| `WARNING: A terminally deprecated method in sun.misc.Unsafe has been called ... netty` | Предупреждение JDK 23 и новее: Netty (через клиент Redis) использует `Unsafe`. Приложение отключает это свойством `io.netty.noUnsafe` в `DocCheckerApplication`. В тестах и при запуске другим способом можно добавить в JVM `--sun-misc-unsafe-memory-access=allow` (только JDK 23+; на JDK 21 флаг вызовет ошибку запуска) |
| Модель не отвечает, в заметках «не ответила за N с» | Увеличьте `app.ollama.read-timeout` или возьмите модель поменьше. Один таймаут не отключает анализ остальных изображений, два подряд отключают |
| У файлов вердикт «не определено», в заметках «Изображения не проанализированы» | Модель недоступна или отключена (`vision-enabled`). Проверьте `GET /api/health` и `ollama list` |
| Модель «не найдена» при старте | `ollama pull <модель>`; при Docker Compose загрузка идёт автоматически, дождитесь состояния healthy |
| Скан PDF не читается | Для сканов в формате JBIG2 в проекте есть `jbig2-imageio`. Если страница не отрисована, файл получает статус «частично» и вердикт «не определено» с пояснением |
| Не открывается результат по ссылке или ID | Результаты хранятся 24 часа; при `app.storage.type=memory` они пропадают при перезапуске |

## Ограничения

- Малые vision-модели (3–4 млрд параметров) плохо читают мелкий текст и рукопись; защиты снижают число ошибок, но не убирают их. Отдельного OCR (Tesseract) и детектора лиц (OpenCV) нет.
- Правила находят ФИО на кириллице; имена латиницей ищет только LLM.
- Не поддерживаются pptx, odt, xls, rar, 7z, tar, webp. Они получают статус `UNSUPPORTED`.
- Не анализируются вложения PDF, векторные тексты в графике PDF, скрытые данные в `docProps` документов Office, содержимое `<script>` в HTML.
- Агент выбирает шаги кодом (оркестратор с журналом), а не свободным выбором инструментов самой моделью.
- Проверки в статусе `RUNNING` не возобновляются после перезапуска сервера.
- Аутентификации нет: сервис рассчитан на внутреннюю сеть.

## Проверка по требованиям

Второй модуль проверяет файл на соблюдение заданных требований.

1. `POST /api/requirement-sets`: загрузить требования (текст или файлы txt, md, docx, pdf). Они разбиваются на отдельные проверяемые пункты.
2. `POST /api/checks`: отправить файл (JPEG, PNG, PDF, DOCX) и `requirementSetId`.
3. `GET /api/checks/{id}`: результат по каждому требованию (`PASS`, `FAIL`, `UNKNOWN`) и краткая сводка.

Подробности: Swagger, разделы «Требования» и «Проверки».
